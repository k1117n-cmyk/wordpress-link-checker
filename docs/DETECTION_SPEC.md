# WordPressサイト リンク切れ検出仕様書

- 作成日：2026/11/16
- 版：0.1（Python無料版の公開用検出仕様）
- 対象：同梱のPython製CLI。操作方法と実行条件は [README](../README.md) を参照。定期運用・通知・サーバー版は含まない。

## 1. 目的と実現可否

WordPressの公開ページからリンクを抽出し、リンク先にHTTP要求を送って、閲覧できないリンクと掲載元を一覧化する。ローカルPCから手動実行する独立したPythonプログラムである。WordPressへのプラグイン追加やデータベース接続は必須としない。

公開HTMLとリンク先のHTTP応答を調べる独立したツールとし、WordPress本体や記事内容を変更しない。

本仕様の数値は既定の上限・要求間隔であり、所要時間の保証ではない。対象サイトの規模やHTTP応答により実際の所要時間は変わる。

## 2. 対象範囲

| 項目 | 初期版の扱い |
|---|---|
| 掲載元ページ | 設定したサイトの公開HTML。投稿・固定ページ・トップページを基本対象とする |
| メニュー・フッター等 | 取得したHTMLに含まれるリンクを対象とする |
| 内部リンク・外部リンク | `a[href]` のHTTP/HTTPSリンクを検査する |
| PDF・画像などへのリンク | `a[href]` に指定されたリンクとしてHTTP応答を検査する |
| 画像表示 | `img[src]` と標準の `img[srcset]` を任意設定で検査する。初期値は無効 |
| ページ内アンカー | `#見出し` の存在検査は初期版対象外。HTTP検査ではフラグメントを除去する |
| 下書き・非公開・ログイン必須ページ | 掲載元として対象外。公開範囲のみを検査する |
| JavaScript実行後に生成されるリンク | 初期版対象外。取得時点のHTMLに存在するリンクのみ対象 |
| CSS背景画像・独自遅延読込属性・フォーム・動画・iframe | 初期版対象外 |
| WordPress本文や設定の修正 | 対象外。リンクの置換・削除は行わない |

外部リンク先は応答確認だけを行い、そのページ内のリンクは巡回しない。HTTPで到達できても、記事内容の正しさ、商品の販売継続、ファイル内容の正常性までは保証しない。

## 3. 掲載元ページの収集

1. 設定されたサイトURLとサイトマップURLを使用する。サイトマップURLの既定候補は `/wp-sitemap.xml` とし、SEOプラグイン独自のURLも明示指定できるようにする。
2. サイトマップインデックスをたどり、設定済みの掲載元オリジン（スキーム・ホスト・ポート）内のURLを収集する。重複・循環を排除する。
3. トップページと、明示指定された追加URLを収集対象に加える。
4. サイトマップが利用できない場合は、設定で選択したREST API方式またはURL一覧方式を使う。REST API方式は公開投稿・固定ページの一覧を取得し、返された公開URLのHTMLを取得する。API本文だけで検査を完結させない。
5. REST APIは `per_page=100` を上限としてページ分割する。総件数・総ページ数と取得件数を記録し、途中失敗を検知する。カスタム投稿タイプは初期版では自動発見せず、サイトマップまたは追加URL一覧から指定する。
6. 対象内リンクからの追加巡回は任意設定とし、初期値は無効。使用時もオリジン・パスの許可範囲と件数上限を守る。

サイトマップ、API、追加巡回のいずれも、サイトの全ページを保証する情報源ではない。収集方法、発見数、取得成功数、取得失敗数、除外数、未処理数を報告する。収集失敗や上限到達があれば「検査未完了」とする。全件収集に失敗した場合も「リンク切れ0件で正常終了」と表示しない。

WordPress標準サイトマップの入口は `/wp-sitemap.xml`。利用可否は設定・プラグイン等の影響を受ける。[WordPress公式：XMLサイトマップ](https://make.wordpress.org/core/2020/07/22/new-xml-sitemaps-functionality-in-wordpress-5-5/)

REST APIの投稿・固定ページ取得とページ分割は公式仕様に従う。[投稿](https://developer.wordpress.org/rest-api/reference/posts/)、[固定ページ](https://developer.wordpress.org/rest-api/reference/pages/)、[ページ分割](https://developer.wordpress.org/rest-api/using-the-rest-api/pagination/)

## 4. リンクの抽出とURLの扱い

- HTMLパーサーで抽出し、相対URL、ルート相対URL、`//example.com/` を絶対URLに変換する。基準は掲載元の転送後URLとし、有効な先頭の `base[href]` があれば反映する。
- HTML文字参照を復元し、要求時には適切なURLエンコードを行う。不正なURLは送信せず、元の表記と理由を報告する。
- スキーム・ホストの大文字小文字と既定ポートを正規化する。パスの大文字小文字、末尾スラッシュ、クエリの値・順序は保持する。クエリ付きURLを一律に同一視しない。
- フラグメントはHTTP要求・重複判定から除去するが、掲載元の表記として保存する。フラグメントだけのリンクと空の `href` はHTTP検査対象外として数える。
- `mailto:`、`tel:`、`javascript:`、`data:` などHTTP/HTTPS以外は対象外とする。
- 送信先URL単位で要求結果を共有し、同じリンクを掲載する全ページと出現箇所を残す。同一ページに複数ある場合も区別する。
- リンク位置は要素種別、同種要素の出現番号、リンク文字列または画像のaltを保存する。投稿本文・メニュー等の領域分類やWordPress編集画面との直接対応は保証しない。
- ログアウト、カート操作、購入、管理画面など副作用を起こし得るパス・クエリを除外する。サイト固有の除外規則を追加できるようにする。通常のGETにもアクセスログ記録等は発生する。

## 5. HTTP確認方法

初期版はGETを使用する。HEADだけではGETと結果が異なるサイトがあるため、HEADの結果だけで判定しない。大きなファイルはストリーミングで受信量を制限し、本文取得を早期終了できるようにする。

| 設定 | 初期値 |
|---|---|
| 接続タイムアウト | 5秒 |
| 1要求の総時間上限 | 20秒（接続・転送を含む） |
| 転送追跡 | 最大5回。各段階のURL・ステータス・Locationを保存 |
| 同時実行数 | 1プロセス内で全体1、同一オリジン1。プロセス間の制御は行わない |
| 同一オリジンへの要求開始間隔 | 1秒以上。再試行・転送・収集要求にも適用 |
| 掲載元HTML受信上限 | 展開後5MiB／ページ |
| リンク先本文受信上限 | 展開後256KiB／要求 |
| 掲載元ページ数上限 | 5,000 |
| 重複排除後のリンク先URL数上限 | 50,000 |
| サイトマップ | 最大100ファイル、深さ5、展開後10MiB／ファイル |
| 1回の実行時間上限 | 2時間 |
| User-Agent | 用途が分かる専用名と版数を明示 |

上限超過時は残りを未処理として終了する。掲載元HTMLが受信上限で切れた場合は、そのページを解析完了と扱わない。XMLは外部実体を無効化して解析する。転送・再試行も実行時間上限に含める。

robots.txtの規則を尊重し、許可されないURLは「除外」とする。robots.txtの取得失敗で可否を判断できない場合は当該オリジンを保留し、未検査として記録する。404の場合は規則なしとして扱う。WAF・認証・CAPTCHAの回避は行わない。

## 6. 判定と再確認

以下は本ツールの分類規則。転送がある場合は最終応答を主判定に用い、途中経過も保持する。

| 結果 | 分類・処理 |
|---|---|
| 200～299 | 到達可能。本文内容・表示の正常性は別問題 |
| 301・302・303・307・308から2xx | 転送あり。リンク切れとは別に一覧化 |
| 404・410 | リンク切れ候補。独立した再GETでも404・410なら「再確認済みリンク切れ」 |
| 401・403 | 認証・拒否のため判定保留。リンク切れとは断定しない |
| 429 | 頻度制限。Retry-Afterに従い、同一オリジンの要求を待機させる |
| 500～599、408、DNS・接続エラー、タイムアウト | 一時障害等として再試行。継続時も到達失敗として分類 |
| TLS証明書検証エラー | TLSエラー。検証を無効化せず、リンク切れと区別 |
| 転送ループ・回数超過・不正な転送先 | 転送異常 |
| その他の3xx・4xx・想定外応答 | 要確認。304も本文再利用条件なしでは到達可能としない |
| 200でエラーページらしい内容 | 任意のサイト別規則に合致した場合のみsoft 404疑い。自動確定しない |

404・410は初回から60秒以上空けて1回再確認する。一時障害等は初回から10秒・60秒以上の間隔で最大2回再試行する。429は有効なRetry-Afterを優先し、なければ60秒以上待機する。指定待機時間が実行期限を超える場合は再送せず保留する。各試行の日時と結果を残し、再確認で2xxなら「再試行で回復」とする。別種のエラーに変わった場合は確定させず要確認とする。

HTTP上の分類と、本当に削除されたかという判断は区別する。404でもアクセス制御等による場合があり、200でもsoft 404やログイン画面の場合がある。[HTTP仕様：RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)、[429とRetry-After：RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)

## 7. 接続先の制限

- HTTP/HTTPSの公開先だけを検査する。URL内のユーザー名・パスワードは受け付けない。ポートは既定で80・443のみ。
- ループバック、プライベート、リンクローカル等の非公開IPを拒否する。IPv4・IPv6の両方を確認する。
- 各要求・転送でDNS解決結果を検証し、実接続先も検証済みIPに限定する。転送先から内部ネットワークへ接続しない。
- 掲載元の巡回許可とリンク先の応答確認を分ける。掲載元が許可範囲外へ転送された場合は巡回を止め、転送先を報告する。
- Cookie・WordPress認証情報は初期版では使用しない。URLクエリに機密情報が含まれる可能性があるため、結果はローカル保存とし、自動公開しない。

## 8. 設定と実行方法

新規の専用設定で、サイト識別子、サイトURL、掲載元オリジンの許可リスト、収集方式、サイトマップURL、追加URL、除外規則、画像検査、追加巡回の有無、負荷・時間上限を指定する。HTTP検査に必要な設定だけを持ち、SSH接続やWordPressの認証情報は使用しない。

実行コマンド（設定例を実サイト用に編集してから使用）：

```sh
python3 bin/check_wordpress_links.py --config conf/linkcheck_example.json
```

本配布物は手動実行用とし、定期実行の設定は含めない。初期版では毎回全対象を検査し、実行をまたいだ成功結果のキャッシュは使用しない。同じサイトの二重起動はロックで防止する。

## 9. 出力

保存先：`reports/linkcheck/<site_id>/<YYYYMMDD_HHMMSS_一意ID>/`。時刻はAsia/Tokyoとし、個々の日時にはタイムゾーンを含める。既存レポートと過去の実行結果は上書きしない。

| ファイル | 内容 |
|---|---|
| `summary.md` | 収集・検査の完了状況、件数、リンク切れ、要確認、未処理、適用設定 |
| `links.tsv` | 掲載元と出現箇所ごとのリンク・最終判定。正常・除外も記録 |
| `requests.jsonl` | 要求ごとの試行日時、URL、方式、応答、転送履歴、エラー、受信打切り有無 |
| `sources.tsv` | 掲載元URLの収集元、取得結果、抽出数、未処理理由 |

`links.tsv` の必須項目：実行ID、サイト識別子、掲載元URL、掲載元タイトル、要素種別、出現番号、リンク文字列／alt、元のURL表記、絶対URL、HTTP確認用URL、最終URL、内部／外部、HTTPステータス、分類、理由、試行回数、初回・最終確認日時。タブ・改行等を規定どおりエスケープし、JSONLから要求履歴を追跡できるようにする。本文全体は保存しない。

要約は「再確認済みリンク切れ」「初回候補」「到達失敗・判定保留」「転送あり」「回復」「未処理」の順に整理する。リンク切れの掲載箇所数と重複排除後のURL数を別々に表示する。除外・不正URL・未対応形式も件数と理由を記録する。

終了コードは `0`＝予定範囲を完了し候補・異常なし、`1`＝完了したが候補または要確認あり、`2`＝収集・解析失敗や上限到達による未完了、`3`＝設定不正・起動不能とする。未完了を優先し、実行できた範囲の問題一覧も保存する。除外を含む検査範囲は終了コード0でも要約に明示する。

## 10. 受入条件

同梱テストでは固定応答とローカルHTTPサーバーを使い、次の検出動作を検証する。実サイトの内容を変更して試験しない。

1. 200、404、410、転送後200、転送後404、転送ループを規定どおり分類できる。
2. 初回404から200へ回復するケースを再確認済みリンク切れにしない。401・403・429・5xx・TLS・DNS・タイムアウトを混同しない。
3. 相対URL、base要素、HTML文字参照、日本語URL、クエリ、フラグメントを仕様どおり処理できる。
4. 同じリンク先への通常検査を共有しつつ、全掲載元・出現箇所を出力できる。
5. REST APIの100件を超えるページ分割と、サイトマップの分割・循環・途中失敗を処理できる。
6. robots.txtの除外・取得失敗、非公開IP、内部IPへの転送、DNS解決先の変化を適切に止める。
7. 同時実行数、要求間隔、Retry-After、受信量・件数・実行時間の上限を守り、打切りを未完了として報告する。
8. 掲載元取得失敗や途中で切れたHTMLを「リンク切れなし」と扱わない。元の要求履歴と要約・TSVの件数が一致する。
9. 設定した対象以外を巡回せず、既存の監視処理・レポートに変更を加えない。

## 11. 配布物と検査結果の限界

配布物は検査プログラム、設定例、README、検出仕様、自動テスト。メール通知・管理画面・記事内リンクの自動修正は含まない。Python 3.11以上と標準ライブラリを利用し、macOS/Linuxを対象とする。Windowsはfcntl非対応のため対象外。

外部サイトはアクセス条件によりブラウザと異なるHTTP応答を返す場合がある。Amazon・YouTube等も同じHTTP分類を使い、自動的な正常扱いや専用の別枠集計は行わない。ブラウザで確認してからリンク修正を判断する。

対象サイトごとの取得成功率、所要時間、全ページの網羅性、外部ページの表示内容を保証しない。収集方式と処理・未処理の内訳を結果ごとに確認する。
